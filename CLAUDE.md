# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project overview

CAN bus CRC / rolling-counter verification tool. Parses DBC files, identifies
Checksum and RollingCounter signals, computes expected values with configurable
algorithms, and compares them with captured traces (BLF, ASC, MF4, TRC, CSV).
Supports AUTOSAR E2E Profile 5 (CRC16/CCITT) and Profile 1/1A
(CRC8/SAE-J1850-ZERO), plus non-CRC checksums (SUM8, SUM8/XOR-FF, XOR8/SEED).

The repository contains **no customer data**. `examples/` is generated by
`examples/generate_example.py` and is the only shipped project.

## Architecture

Leaf modules (`crc/`, `dbc/`, `trace/`, `dataid/`, `patterns.py`, `bit_utils.py`)
do not depend on each other. `protect/` depends on `crc/` + models. `verify/`
assembles everything. `report/` consumes `verify/` models only.

- **`crc_checker/patterns.py` + `crc_checker/data/patterns.yaml`** — signal-name
  rules (prefix/suffix regexes, block-counter exclusion, bus-marker stripping,
  suffix-detection threshold). `signals.patterns_file` selects a custom YAML;
  `signals.checksum_pattern` / `signals.rc_pattern` are single-regex overrides.
  Never hard-code naming conventions in the resolver.
- **`crc_checker/crc/`** — lookup-table CRC engine (`engine.py`, CRC8/16/32 and
  the non-CRC `sum` / `sum_xor` / `xor_seed` types), presets (`presets.py`,
  including the validation registry), E2E profile table (`profiles.py`: `p01` /
  `p05`, selected by DataID hint or CRC width), and DBC-comment classification
  (`classify.py`: Profile 1A / 5, SAE-J1850, SUM8, SUM8/XOR-FF, XOR8/SEED, skip).
  `CRCParams` is frozen and cached by value in `CRCVerifier`.
- **`crc_checker/dbc/`** — `parser.py` wraps canmatrix (encoding auto-detected
  utf-8 → gbk → latin-1); `resolver.py` applies the configured patterns and
  pairs checksums with counters (indexed instances stay separate groups; bus
  markers are stripped; block counters never count as rolling counters).
  `models.py` holds `DBCProtectionMap`, `ChannelProtectionMap`,
  `MessageProtection` and the `apply_*` mutators.
- **`crc_checker/dataid/`** — Excel (`.xlsx` / legacy `.xls`) and JSON DataID
  parsing. Named column layouts come from
  `crc_checker/data/dataid_mappings.yaml`; `dataid.mapping_file` loads a custom
  YAML. Entries are registered under the message name and under a CRC signal
  named in a remark column; `get_normalized()` matches ignoring underscores/case.
- **`crc_checker/trace/`** — python-can reader; `CanFrame` dataclass.
- **`crc_checker/protect/`** — `CRCVerifier` (stateless, DataID injection,
  byte-swap) and `RollingCounterVerifier` (stateful per frame-id/signal; PASS,
  STALE, SKIP, RESET, INVALID). Consecutive failures fold into one verdict with
  `repeat_count`, while every sample stays in `get_series()`.
- **`crc_checker/verify/`** — `engine.py` runs the per-frame loop; `runner.py` is
  the single "DBC selection → DataID → CRC config → verify" implementation used
  by both the CLI and the web API.
- **`crc_checker/report/`** — self-contained HTML report with CRC/RC byte
  highlighting and per-signal RC trend charts. `trends.py` also owns the
  sample-based accounting helpers. Reports above `REPORT_FULL_MAX_SECTIONS`
  (default 30 000, configurable via `output.max_report_sections`) downgrade to a
  failures-only view and say so in the report; aggregates always count
  frames/samples, never folded verdicts.

### Web version

`webapp/` (FastAPI) + `frontend/` (Vue 3 + Element Plus; `frontend/dist` is
committed). `webapp/catalog.py` scans `projects/` (or `CRC_CHECKER_PROJECTS_DIR`,
falling back to `examples/`) and exposes project **ids** only — the browser never
sends paths. `webapp/service.py` bridges the shared runner to the web and caches
finished runs (LRU 20) under `data/web/runs/<run_id>/`. `webapp/version.py`
reports the running commit vs. the deploy directory commit. See
[docs/web-api.md](docs/web-api.md).

### Adding capabilities

- **New signal naming** → add a regex to `crc_checker/data/patterns.yaml`.
- **New DataID workbook layout** → add a named mapping to
  `crc_checker/data/dataid_mappings.yaml`.
- **New CRC algorithm** → add a preset to `crc_checker/crc/presets.py` and its
  validation status; add a known-answer test.
- **New project** → put `config.json` (+ DBC/DataID/trace) under `projects/`.

## Testing

`tests/` covers CRC known vectors, comment classification, GBK DBC decoding,
resolver matching, custom patterns, profile/DataID logic, RC folding and trend
charts, report size limits, the web layer (catalog, version, API, run store), and
the synthetic example end to end. The frontend's pure-logic tests run with
`cd frontend && npm test`.
